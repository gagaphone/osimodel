What Is the OSI Model?

The Open Systems Interconnection (OSI) model is a conceptual framework developed by the International Organization for Standardization (ISO). Published in the 1980s, it organizes network communication into seven layers, each with a distinct role.

As data travels through the model, each layer provides services to the layer above it and uses services from the layer below it. This layered approach helps explain network communication, design, and troubleshooting.

The OSI model is a reference model rather than a protocol suite. Real-world internet communication is primarily based on the TCP/IP model, while the OSI model remains a useful framework for learning and diagnosing network problems.

77 Protocol Entries

Why does the OSI model matter?

  • Interoperability: Helps explain how systems from different vendors communicate using common standards.
  • Troubleshooting: Helps narrow a fault down to a likely layer, such as a cable, VLAN, route, or application.
  • Protocol design: Provides a structured way to understand networking functions.
  • Learning: Gives networking students and certification candidates a common reference framework.

Layer 1 — Physical

The Physical Layer transmits raw binary data across a physical medium. It deals with signals, timing, connectors, physical topology, and the characteristics of cables or radio.

PDU
Bit (1s and 0s)
Responsibilities
Signal encoding, bit timing, physical media, duplex settings
Examples
Ethernet copper, fibre optic cable, Wi-Fi radio, DSL, coaxial cable
Devices
Cables, connectors, hubs, repeaters, transceivers
Typical fault
Damaged cable, disconnected port, bad transceiver, incorrect cable distance
Real-world example: A user has no network connection. Check that the cable is connected and the switch-port link light is on, then test with a known-good cable.
Layer 2 — Data Link

The Data Link Layer organizes bits into frames and supports delivery across a local network link. Ethernet and Wi-Fi use link-layer addressing and media-access mechanisms.

PDU
Frame
Sub-layers
LLC (Logical Link Control) and MAC (Media Access Control)
Addressing
MAC addresses, commonly represented as six hexadecimal octets
Protocols
Ethernet, Wi-Fi, PPP, VLAN tagging, STP, LACP
Devices
Switches, bridges, wireless access points, network adapters
Typical fault
VLAN mismatch, switching loop, MAC-learning issue, frame errors
Real-world example: A switch learns source MAC addresses and uses its MAC address table to forward frames toward the correct port.
Layer 3 — Network

The Network Layer provides logical addressing and routes packets between different IP networks. Routers inspect destination IP addresses and consult their routing tables.

PDU
Packet
Addressing
IPv4 (32-bit) and IPv6 (128-bit)
Protocols
IP, ICMP, OSPF, EIGRP, RIP, BGP
Devices
Routers, Layer 3 switches, packet-filtering firewalls
Typical fault
Missing route, wrong subnet mask, incorrect default gateway
Real-world example: A host sends a packet to a server on another network. A router checks its routing table and forwards the packet toward the destination network.
Layer 4 — Transport

The Transport Layer supports communication between application processes on different hosts. Transport ports identify the source and destination application endpoints.

PDU
TCP segment or UDP datagram
Protocols
TCP, UDP, SCTP
TCP
Connection-oriented transport with sequencing, acknowledgements, retransmission, and flow control
UDP
Connectionless transport with lower overhead and no built-in retransmission
Typical fault
Blocked port, failed TCP handshake, wrong port configuration
TCP vs. UDP: A conventional web connection using HTTP/1.1 or HTTP/2 typically uses TCP. Many real-time applications use UDP where reducing delay is important. HTTP/3 uses QUIC over UDP.
Layer 5 — Session

The Session Layer describes functions for establishing, maintaining, coordinating, and terminating conversations between applications. Session functions may include dialogue control and checkpoints.

PDU
Data
Examples
NetBIOS session services, RPC, SMB, NFS, and session-related functions in applications
Functions
Session establishment, maintenance, graceful termination, checkpoints
Typical fault
Session timeout, authentication failure, session limits
Real-world note: In modern TCP/IP systems, session functionality is often implemented by application protocols and software rather than a separate visible layer.
Layer 6 — Presentation

The Presentation Layer describes how data is represented so that different systems can interpret it consistently. Related functions include encoding, serialization, encryption, and compression.

PDU
Data
Encoding
ASCII, Unicode, EBCDIC
Data formats
JSON, XML, JPEG, GIF, MPEG, MP3
Security
TLS provides encryption in modern network stacks; its placement in OSI is a conceptual simplification
Typical fault
Encoding mismatch, certificate problem, incompatible data format
Real-world example: Applications encode text as UTF-8 and may compress content before transmitting it. Secure connections use TLS to protect data in transit.
Layer 7 — Application

The Application Layer provides network protocols and services used by software such as browsers, mail clients, file-transfer tools, and management applications. It describes the protocol interface, not the application program itself.

PDU
Data
Web
HTTP and HTTPS
Email
SMTP, IMAP, POP3
Other protocols
FTP, SFTP, DNS, DHCP, SNMP, SSH, Telnet
Typical fault
Incorrect URL, application configuration, unavailable service, DNS lookup issue
Real-world example: A browser requests a page using HTTP or HTTPS. DNS may first resolve the domain name to an IP address so the browser can connect to the destination.

HOW DATA MOVES

Encapsulation and Decapsulation

Encapsulation occurs as data moves down the sender's stack: each layer adds information needed for delivery. Decapsulation occurs at the receiver, where the appropriate headers and trailers are examined and removed.

Sender: Encapsulation ↓

Layer 7 · Application HTTP data
Layer 4 · Transport TCP header | HTTP data
Layer 3 · Network IP header | TCP segment
Layer 2 · Data Link Ethernet header | IP packet | FCS
Layer 1 · Physical Bits: 10101001 01101101 ...
Across the physical medium ⇄ Electrical, optical, or radio signals

Receiver: Decapsulation ↑

Layer 1 · Physical Signals become bits
Layer 2 · Data Link Check frame and remove link header
Layer 3 · Network Inspect IP packet and destination
Layer 4 · Transport Process transport ports and data
Layer 7 · Application Deliver HTTP data to the service

Physical travel vs. logical communication

Bits physically travel over the medium. Other layers communicate logically with their corresponding peer layers through protocol rules and headers. This is why a Layer 4 protocol can define end-to-end behavior even though the transmitted bits pass through Layer 1.

RELATED NETWORK MODEL

OSI Model vs. TCP/IP Model

The TCP/IP model describes the protocol architecture commonly used for internet communication. In its four-layer version, several OSI layers are grouped together.

OSI Layer TCP/IP Four-Layer Model Examples
7 — Application Application HTTP, HTTPS, DNS, DHCP, SMTP, SSH
6 — Presentation Application Data formats, encoding, encryption functions
5 — Session Application Session and dialogue functions
4 — Transport Transport TCP, UDP
3 — Network Internet IPv4, IPv6, ICMP, routing
2 — Data Link Network Access / Link Ethernet, Wi-Fi, PPP, VLAN
1 — Physical Network Access / Link Cables, optical signals, radio signals

Key difference

The four-layer TCP/IP model groups the OSI Session, Presentation, and Application functions into its Application layer, and groups the Physical and Data Link functions into Network Access. Five-layer TCP/IP diagrams often separate the link and physical functions for teaching.

PRACTICAL NETWORKING

Troubleshooting by OSI Layer

The OSI model provides a structured approach to network troubleshooting. Start at Layer 1 (Physical) and work upward toward Layer 7 (Application). This approach helps identify problems systematically instead of randomly changing network settings.

This reference includes practical troubleshooting commands for Linux, Windows, and macOS, together with common network problems and diagnostic techniques.

Important troubleshooting principle

Always verify lower network layers before investigating higher layers. If a network cable is disconnected or a Wi-Fi adapter is disabled, testing DNS or HTTP will not resolve the underlying connectivity problem.

1. Layer 1 — Physical Layer

PDU: Bits
Focus: Physical connectivity

The Physical Layer is responsible for transmitting raw bits through physical media such as Ethernet cables, fiber-optic connections, and wireless signals.

Purpose: Check cables, network interfaces, Wi-Fi signal strength, link status, and physical connectivity.

Diagnostic commands

Linux Windows macOS
ip link Get-NetAdapter ifconfig
ethtool eth0 Get-NetAdapterStatistics networksetup -listallhardwareports
nmcli device status Get-NetAdapter -Physical ifconfig en0
iw dev netsh wlan show interfaces wdutil info

Common problems and what to check

Problem Possible cause What to check
Network cable disconnected Loose or damaged connection Inspect cable, connector, and switch port.
Network interface disabled Adapter administratively disabled Check adapter status and enable the interface if appropriate.
No link detected Failed NIC, cable, or switch port Test with a known-good cable and switch port.
Wi-Fi disconnected Incorrect credentials or disconnected adapter Check SSID, password, and wireless adapter status.
Weak Wi-Fi signal Distance or wireless interference Check signal strength and access point placement.
Incorrect link speed Speed or duplex negotiation issue Inspect interface speed and duplex settings.
Hardware failure Faulty network adapter Inspect adapter status and system logs.

Useful indicators

  • Linux: Look for LOWER_UP in ip link.
  • Windows: Look for Status = Up in Get-NetAdapter.
  • macOS: Look for status: active in ifconfig.

Note: Replace eth0 with your actual interface name. The ethtool utility may need to be installed on Linux.

4. Layer 4 — Transport Layer

PDU: Segment (TCP) / Datagram (UDP)
Focus: Ports and connections

The Transport Layer provides end-to-end communication using TCP and UDP. It handles port addressing, connection establishment, reliability, and flow control.

Purpose: Troubleshoot TCP and UDP communication, port availability, connection establishment, and firewall filtering.

Diagnostic commands

Linux Windows macOS
ss -tulnp netstat -ano netstat -an
ss -ant Get-NetTCPConnection lsof -i -P
nc -vz host 443 Test-NetConnection host -Port 443 nc -vz host 443
sudo tcpdump -i eth0 tcp pktmon sudo tcpdump -i en0 tcp
nmap -sT host nmap -sT host nmap -sT host

Common problems and troubleshooting

Problem Possible cause Troubleshooting
Connection refused No service listening on the port Check listening ports and application services.
Connection timeout Firewall filtering or unreachable host Test connectivity and firewall rules.
Port already in use Another process occupies the port Identify the process using the port.
TCP handshake failure SYN packets not answered Capture and inspect TCP traffic.
TCP connection reset Server, firewall, or application reset Inspect TCP RST packets.
UDP application not responding UDP filtering or service issue Check UDP service and capture traffic.
Too many connections Connection exhaustion Inspect active connections and limits.
Firewall blocking port Inbound or outbound filtering Review firewall rules and policies.

Useful command examples

Linux

ss -ant
nc -vz example.com 443

Windows

netstat -ano
Get-NetTCPConnection
Test-NetConnection example.com -Port 443

macOS

lsof -i -P

Windows tip

Test-NetConnection is particularly useful for checking TCP connectivity to a specific port. It reports whether the remote TCP connection succeeded.

Nmap must be installed separately. Packet capture and some connection inspection commands may require administrator privileges. A successful TCP test does not prove that the application itself works.

8. Practical Troubleshooting Workflow

When a user reports that they cannot access the internet, follow a structured troubleshooting sequence from Layer 1 to Layer 7.

Layer What to investigate Useful commands
L1 — Physical Is the cable connected? Is Wi-Fi enabled? ip link / Get-NetAdapter / ifconfig
L2 — Data Link Is local network communication working? Is ARP resolving? ip neigh / arp -a
L3 — Network Is the IP configuration and default gateway correct? ip route / ipconfig /all / ping
L4 — Transport Is the required TCP or UDP port reachable? nc -vz host 443 / Test-NetConnection
L5 — Session Can remote sessions be established and maintained? smbstatus / query session
L6 — Presentation Is TLS negotiation successful? Is the certificate valid? openssl s_client
L7 — Application Does DNS resolve? Does the application respond? dig / nslookup / curl

10. Example: Troubleshooting a Website That Does Not Open

Imagine a user reports: "I cannot access https://www.example.com."

Follow these steps to identify where the problem occurs.

Step Command (Windows example) What you are testing
1 ipconfig /all IP configuration and default gateway.
2 ping <gateway-ip> Local gateway connectivity.
3 ping 8.8.8.8 External IP connectivity.
4 nslookup example.com DNS name resolution.
5 Test-NetConnection example.com -Port 443 TCP connectivity to HTTPS port 443.
6 curl.exe -v https://example.com HTTPS and application response.
7 openssl s_client -connect example.com:443 -servername example.com TLS handshake and certificate details.

How to interpret the results

  • Step 1 fails or shows invalid configuration: Investigate interface configuration, DHCP, and Layers 1–3.
  • Step 2 fails: Investigate local connectivity, VLAN configuration, and gateway reachability.
  • Step 3 fails: Investigate routing, firewall rules, and upstream connectivity. Also remember that ICMP may be blocked.
  • Step 4 fails: Investigate DNS configuration and name resolution.
  • Step 5 fails: Investigate TCP connectivity, port availability, and firewall filtering.
  • Step 6 fails: Investigate HTTP/HTTPS responses, TLS, and application behavior.
  • Step 7 fails: Investigate TLS configuration, certificates, and encryption.

Important troubleshooting note

A failed ping does not automatically mean the destination is unavailable. Firewalls and network devices may block ICMP while allowing normal TCP application traffic.

Likewise, a successful ping does not prove that DNS, HTTPS, or the application is working correctly.

For Linux and macOS, substitute the corresponding commands from the diagnostic tables above.

11. Additional Recommendation: Packet Analysis

If you want to become proficient in network troubleshooting, learn to use Wireshark and tcpdump. Packet analysis allows you to inspect network traffic and identify problems that ordinary connectivity commands cannot explain.

Wireshark

Wireshark is a graphical network protocol analyzer. It is useful for inspecting packets across multiple OSI layers, investigating protocol errors, and analyzing communication between devices.

Visit the official Wireshark website

tcpdump

tcpdump is a command-line packet analyzer commonly used on Linux and macOS. It captures and filters packets directly from network interfaces.

Visit the official tcpdump website

Useful Wireshark display filters

Display filter Purpose
arp ARP requests and responses.
icmp Ping and ICMP traffic.
dns DNS requests and responses.
tcp TCP traffic.
udp UDP traffic.
http HTTP traffic.
tls TLS traffic.
tcp.port == 443 TCP traffic involving port 443.
ip.addr == 192.168.1.10 Traffic involving a specific IPv4 address.

Useful tcpdump examples

# Capture DNS traffic
sudo tcpdump -i eth0 port 53

# Capture ICMP traffic
sudo tcpdump -i eth0 icmp

# Capture TCP traffic on port 443
sudo tcpdump -i eth0 tcp port 443

# Capture traffic involving a specific host
sudo tcpdump -i eth0 host 192.168.1.10

# Capture and save packets to a file
sudo tcpdump -i eth0 -w capture.pcap

Replace eth0 with your actual network interface. Capturing traffic may require administrator privileges. Follow organizational policies and obtain authorization before capturing network traffic.

12. Final Troubleshooting Recommendations

The most effective way to troubleshoot network problems is to understand what each OSI layer does and learn the commands used to investigate it.

  • Start with Layer 1 and verify physical connectivity.
  • Check Layer 2 for MAC addressing, ARP, and VLAN problems.
  • Verify Layer 3 IP configuration, gateways, and routing.
  • Test Layer 4 TCP/UDP ports and firewall rules.
  • Investigate Layer 5 session establishment and persistence.
  • Check Layer 6 TLS, certificates, and data encoding.
  • Finish with Layer 7 DNS, HTTP, and application services.
  • Use Wireshark and tcpdump when command-line tests are insufficient.

Key takeaway

The OSI model is a troubleshooting framework, not a strict boundary between operating-system commands. Many commands inspect multiple layers. Layers 5 and 6 are particularly conceptual in modern TCP/IP networks, where session and presentation functions are often integrated into application protocols and libraries.

Learn the commands layer by layer, then practice diagnosing real-world scenarios such as DHCP failures, DNS problems, incorrect VLAN configuration, routing issues, blocked ports, and TLS certificate errors.

Important Note About Layer Mappings
